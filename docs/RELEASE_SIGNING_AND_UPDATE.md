# توقيع Windows وإطلاق تحديثات GitHub

## ما تم داخل المشروع

- `electron-updater` مضاف إلى dependencies.
- `electron-builder.yml` مضبوط على GitHub Releases.
- التطبيق ينشئ نسخة احتياطية قبل تثبيت التحديث.
- التثبيت التلقائي لا يبدأ دون تنزيل ناجح.

## ما يجب تنفيذه خارج بيئة الوكيل

### 1. شراء شهادة Code Signing

اشترِ شهادة توقيع Windows من مزود موثوق، ويفضل شهادة مخزنة في token/HSM أو خدمة توقيع آمنة.

لا تضع ملف الشهادة أو كلمة مرورها في Git.

### 2. إنشاء أسرار GitHub Actions

أضف الأسرار إلى Repository Settings → Secrets and variables → Actions، مثل:

```text
CSC_LINK
CSC_KEY_PASSWORD
```

حسب طريقة مزود الشهادة.

### 3. تفعيل التوقيع في CI

عدّل Workflow ليستخدم أسرار التوقيع أثناء:

```bash
npm run package:win
```

ثم تحقق من التوقيع على Windows:

```powershell
Get-AuthenticodeSignature .\dist\RAFD-Setup-0.1.0.exe
```

يجب أن تكون الحالة `Valid` وأن يظهر الناشر الصحيح.

### 4. إنشاء Release

بعد نجاح التثبيت والتوقيع:

```bash
gh release create v0.1.0 dist/RAFD-Setup-0.1.0.exe --title "RAFD v0.1.0" --generate-notes
```

لا تنشئ Release تجاريًا قبل التأكد من:

- وجود التوقيع.
- وجود installer وملفات latest metadata.
- نجاح smoke على Windows.
- وجود نسخة rollback.

### 5. اختبار التحديث

1. ثبّت الإصدار السابق.
2. أنشئ بيانات ومبيعات ونسخة احتياطية.
3. أنشئ Release جديدًا مثل `v0.1.1`.
4. شغّل فحص التحديث من شاشة الإدارة.
5. نزّل التحديث.
6. تحقق من وجود النسخة الاحتياطية قبل التثبيت.
7. ثبّت التحديث.
8. تحقق من migrations والبيانات.
9. اختبر فشل التحديث والرجوع للإصدار السابق.

## قيود مهمة

- GitHub Releases العامة مناسبة فقط إذا كان المستودع/التوزيع يسمح بذلك.
- Releases الخاصة تحتاج آلية مصادقة لا يجوز تضمينها داخل التطبيق بصورتها الخام.
- يجب اتخاذ قرار نهائي حول توزيع تحديثات العملاء قبل الإطلاق التجاري.
